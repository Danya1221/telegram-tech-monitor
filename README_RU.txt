QUANTUM / TECH MONITOR — CLEAN BUILD

Это чистая актуальная сборка.

Файлы:
- main.py — бот + мониторинг
- requirements.txt — Python зависимости
- railway.json — Railway запускает python main.py
- Procfile — запасной start command
- .env.example — список переменных без секретов

ВАЖНО ПРИ ПЕРЕЗАЛИВКЕ
1. Не запускай одновременно старый и новый Service.
2. Лучше создать НОВЫЙ Railway Service/Project из этой папки.
3. Подключи PostgreSQL.
4. Добавь Variables:
   API_ID
   API_HASH
   BOT_TOKEN
   DATABASE_URL
   ADMIN_ID
   ANALYTICS_TZ
5. Deploy.
6. Подключи Telegram-аккаунт(ы) через /login.
7. Выбери чаты заново при необходимости.
8. Добавь запросы заново.

АКТИВНЫЙ СПИСОК ЗАПРОСОВ
Сборка использует только новую таблицу:
monitor_queries_v2

Старая таблица queries не участвует в поиске.

ЗАПРОСЫ
- список разбит по 8 позиций на страницу;
- удаление тоже постраничное;
- каждая кнопка удаления привязана к конкретному ID;
- после удаления страница перечитывается из PostgreSQL;
- пустой список = монитор ничего не матчится по запросам.

MATCHING
В сборке уже есть исправления:
- PlayStation 5 Pro не ловит MacBook Pro;
- Ray-Ban Meta не ловит Meta Quest / sport band / Blu-Ray;
- S26 не ловит S26 Ultra / Plus / Edge;
- S26 Black выбирает только подходящую строку каталога;
- iPhone 17 не ловит iPhone 17 Pro;
- цвета / память / eSIM / модификации модели проверяются строго;
- опечатки и транслитерация по-прежнему поддерживаются.

УВЕДОМЛЕНИЯ
Задержка: 15 секунд.
Перед отправкой запрос повторно проверяется в базе.
Если за время задержки запрос удалён, уведомление отменяется.

АНТИДУБЛЬ
Одинаковый продавец + одинаковый нормализованный запрос
в нескольких чатах подряд подавляется на 120 секунд.

ПРОВЕРКА

MULTILINE PRODUCT FIX
Одна товарная позиция может быть разбита на 1–4 соседние строки.
Бот собирает такой блок для проверки, но в уведомление не тащит
весь длинный прайс.


ALL-REQUEST ANALYTICS
Аналитика больше НЕ зависит от списка отслеживания.

Считаются покупательские запросы во всех выбранных чатах:
- ищу / ищем
- куплю / купим
- нужен / нужна / нужно / нужны
- интересует
- возьму
- предложите / предлагайте
- кто продаст
- есть у кого
- WTB / wanted / looking for / need / buying

Продажи вроде "продам", "в наличии", WTS в аналитику спроса не входят.

Уведомления по-прежнему приходят только по monitor_queries_v2.

Новая аналитика хранится отдельно:
all_request_analytics_events

Старая matched-only analytics_events не смешивается с новой статистикой.
После обновления новая аналитика начинает накапливаться с нуля.


INTERESTING QUERIES / ИНТЕРЕСУЮЩИЕ ЗАПРОСЫ

В главном меню добавлен отдельный раздел:
⭐ Интересующие

Это полностью независимый список:
- хранится в interest_queries_v1;
- НЕ включает уведомления;
- НЕ добавляется в monitor_queries_v2;
- НЕ меняет обычный поиск;
- используется только для отдельного подсчёта спроса.

Внутри раздела:
- добавить интересующие позиции;
- удалить позиции;
- пагинация по 8;
- отдельная статистика Сегодня / 7 дней / 30 дней.

Статистика берёт уже собранные события из all_request_analytics_events,
поэтому если добавить новую интересующую позицию, она может посчитать
её и по уже накопленной общей аналитике.

Каждое сообщение считается максимум один раз — оно относится к
лучше всего совпавшей интересующей позиции.

RAM / STORAGE CONFIGURATION BREAKDOWN

Для интересующих моделей теперь отдельно считаются конфигурации RAM/памяти.

Пример:
Samsung A57

В статистике:
- Samsung A57 6/256 — 4
- Samsung A57 8/256 — 13
- Samsung A57 12/256 — 6
- Samsung A57 8/128 — 2

Разные конфигурации НЕ склеиваются:
6/256 != 8/256 != 12/256

Одинаковые способы записи склеиваются:
8/256
8+256
8-256
8 x 256
8GB/256GB
8 ГБ + 256 ГБ
=> одна конфигурация 8/256

Поддерживаются накопители 1TB / 2TB / 4TB.

Защита от ложного определения:
A57 256 не превращается в 57/256, потому что 57 не является допустимым RAM.


SECOND ACCOUNT LOGIN FIX

Исправлена привязка второго Telegram-аккаунта.

Раньше:
- /login создавал временный Telethon client только в RAM;
- FSM тоже был MemoryStorage;
- при Railway restart / смене процесса следующий номер или код
  мог потеряться;
- после номера бот мог молчать.

Теперь:
- состояние логина хранится в PostgreSQL:
  telegram_login_flows_v1
- после ввода номера бот СРАЗУ пишет:
  "Номер принят. Запрашиваю код..."
- временная StringSession и phone_code_hash сохраняются между шагами;
- номер -> код -> 2FA переживают restart процесса;
- Telethon login client создаётся заново на каждом этапе;
- receive_updates=False во время авторизации;
- connect/request имеют таймауты;
- при ошибке показывается тип ошибки, а не молчание;
- после успешного входа временная login-запись удаляется.

Обычные monitor clients, matcher, queries и analytics не изменены.


SECOND ACCOUNT LOGIN V9

Дополнительный fix:
- после send_code_request Telethon client БОЛЬШЕ не отключается;
- тот же client используется для sign_in(code);
- тот же client используется для 2FA password;
- PostgreSQL StringSession остаётся fallback только после Railway restart;
- после ввода кода бот СРАЗУ отвечает:
  "Код принят. Проверяю..."
- после ввода 2FA бот СРАЗУ отвечает:
  "Пароль принят. Проверяю..."
- скрытая аварийная команда:
  /code 1 2 3 4 5

Если после обычного сообщения с кодом нет даже "Код принят",
то этот update не попал в текущий v9 process (обычно параллельный старый bot poller).
